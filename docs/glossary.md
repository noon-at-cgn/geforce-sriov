# Glossary

Terms used in the guides and reference pages.

| Term | Meaning |
|---|---|
| <a id="pf"></a>**PF** (physical function) | The card itself as the PCI bus sees it, for example `0000:01:00.0` |
| <a id="bdf"></a>**BDF** | A PCI address in the form `domain:bus:device.function`, as in `/sys/bus/pci/devices` |
| <a id="sr-iov"></a>**SR-IOV** | A PCIe feature that lets one device appear as several lightweight devices |
| <a id="vf"></a>**VF** (virtual function) | One of those lightweight devices. Each can back one vGPU. By default 4 are presented per card, set by `vfs`. NVIDIA's patched driver uses at most 4 |
| <a id="ari"></a>**ARI** | A PCIe addressing extension that allows more functions per device. The `geforce_sriov` kernel module reveals the card's hidden ARI and turns on ARI forwarding in the bridge above it. This is the `ari=on` setting. More than 4 VFs per card is not available, so 4 is the default |
| <a id="msi-x"></a>**MSI-X** | A way for a device to send interrupts. The `geforce_sriov` kernel module reveals the card's hidden MSI-X (`msix=on`) |
| <a id="vgpu"></a>**vGPU** | NVIDIA's software that gives each VM a slice of one GPU. Each vGPU has a type, also called a profile, such as `RTXA6000-4Q`. The type fixes its memory size |
| <a id="mdev"></a>**mdev** (mediated device) | How legacy vGPU creates each vGPU on GPUs without SR-IOV. Here each VM gets a VF instead. The VF is attached as a plain VFIO PCI device with the vGPU type already set. See [Create a VM](installation.md#create-a-vm) |
| <a id="iommu"></a>**IOMMU** | The hardware that keeps each VM's device access separate. It must be enabled |
| <a id="livepatch"></a>**Livepatch** | A kernel feature that replaces functions of a running kernel without a reboot. The `geforce_sriov` kernel module is a livepatch. It replaces three PCI functions of the kernel: `pci_find_ext_capability`, `pci_read_config_word` and `pci_write_config_word`. It changes their answers only for the cards you selected |
| <a id="dkms"></a>**DKMS** | A framework that rebuilds out-of-tree kernel modules automatically for each new kernel |
| <a id="boot-display"></a>**Boot display** | The GPU that shows BIOS/UEFI startup messages before Linux loads, and the local text console with its login prompt, on its connected monitor. Its `boot_vga` is `1` in sysfs. See [Boot display GPU](installation.md#boot-display-gpu) |
| <a id="gsp"></a>**GSP** | The GPU System Processor. It runs part of NVIDIA's driver as firmware. NVIDIA's stock vGPU host driver uses it on Ada but not on Ampere. geforce-sriov loads the host driver with `NVreg_EnableGpuFirmware=0` on both generations. The core of the driver then runs on the host CPU. NVIDIA calls this core the Resource Manager (RM), or CPU-RM when it runs on the host CPU. See [Ada host stack](ada.md#host-stack) |
| <a id="driver-flavour"></a>**Driver flavour** | NVIDIA's Linux kernel module comes in a proprietary and an open flavour. geforce-sriov supports only the proprietary one. See [NVIDIA driver flavour](devices.md#nvidia-driver-flavour) |
| <a id="vgpu-type"></a>**vGPU type** | The fixed size of a vGPU. NVIDIA also calls it a profile. The name ends in the memory size. For example, `4Q` in `RTXA6000-4Q` means a 4 GB framebuffer. See [Choosing a vGPU type](installation.md#choosing-a-vgpu-type) |
| <a id="vgpu-plugin"></a>**vGPU plugin** | NVIDIA's `libnvidia-vgpu.so`, which `nvidia-vgpu-mgr` loads to run vGPUs. `install` makes a patched copy of your own plugin file and points the `libnvidia-vgpu.so` link at it |
| <a id="boot-unit"></a>**Boot unit** | One of two systemd services that `install` enables. `geforce-sriov-livepatch.service` loads the `geforce_sriov` kernel module and NVIDIA's driver. `geforce-sriov-activate.service` runs `activate` to bring the GPUs up at each boot. See [Systemd units](configuration.md#systemd-units) |
| <a id="identity-hook"></a>**Identity hook** | A small library loaded into NVIDIA's `nvidia-vgpud` daemon. It presents each selected card under its professional counterpart's device ID, so that NVIDIA's vGPU software accepts the card. The daemon loads it through `LD_PRELOAD`, a setting that makes a process load a given library first. See [The identity hook](technical-reference.md#the-identity-hook) |
| <a id="display-modules"></a>**Display modules** | The kernel modules `nvidia-modeset` and `nvidia-drm`. They let the boot display GPU keep its display working while it serves VFs. `install` builds them from the Linux driver package and NVIDIA's public kernel module source. See [What to download](installation.md#what-to-download) |
| <a id="kms"></a>**KMS** (kernel mode setting) | The part of a display driver that sets the screen mode and drives the display, console or desktop. Here it goes only to the boot display GPU |
| <a id="d3cold"></a>**D3cold** | A PCIe power state in which a device is powered off. A laptop GPU can enter it when idle, which erases its SR-IOV setup. See [D3cold](laptops.md#d3cold) |
| <a id="activation-lock"></a>**Activation lock** | The file `/var/lib/geforce-sriov/prepare-attempt`. `activate` writes it when an activation is incomplete or its state is uncertain, and removes it when the run finishes cleanly. While it is set, activation refuses to run. See [The activation lock](recovery.md#the-activation-lock) |
| <a id="cold-power-cycle"></a>**Cold power cycle** | Switching the machine fully off and on, **not** rebooting. A card that stopped answering or an activation that did not finish gets back to a known state only after the card loses power. See [The one rule](recovery.md#the-one-rule) |
| <a id="unbindlock"></a>**unbindLock** | A file in `/proc/driver/nvidia/gpus/<BDF>/` through which NVIDIA's driver says whether a GPU is free. `activate` removes or re-probes a card only after the lock is granted, which means no program holds the GPU |
| <a id="pci-ids"></a>**PCI vendor ID, device ID, subsystem ID** | The numbers a PCI device reports to identify itself. The vendor ID names the maker, and `10de` is NVIDIA. The device ID names the chip or card model, for example `2206`. The subsystem ID names the board maker's variant. `lspci -nn` shows them. geforce-sriov matches cards by device ID and presents each one under its professional counterpart's ID |
| <a id="config-space"></a>**Config space** | The small block of registers every PCI device exposes so the system can discover and configure it. It holds the device's capabilities, such as SR-IOV, ARI and MSI-X. The addresses in the docs are offsets into it. Two examples are `0xBCC` and `0x41C` |
| <a id="bar"></a>**BAR, memory window** | A BAR (base address register) is a range of the machine's address space that a device uses to expose its memory and registers. The bridges above the card must have a window large enough for the BARs of the card and of every VF. Otherwise a VF cannot be assigned its memory |
| <a id="framebuffer"></a>**Framebuffer** | Video memory that holds an image. For the boot display GPU it is the memory the screen is drawn into. The firmware sets one up at boot, and `activate` hands it over to NVIDIA's display modules. For a vGPU it is the VRAM the vGPU gets, which the number in its type name states: `4Q` is 4 GB |
| <a id="vfio"></a>**VFIO** | The Linux framework that lets a VM use a PCI device directly. QEMU attaches a VF to a guest as a `vfio-pci` device |
| <a id="kernel-module"></a>**Kernel module** | Code that the Linux kernel loads on demand, such as NVIDIA's `nvidia.ko`. A kernel module is built against one specific kernel version |
| <a id="udev"></a>**udev** | The part of systemd that loads drivers automatically when it sees hardware. geforce-sriov keeps udev from loading `nvidia` on its own, because the `geforce_sriov` kernel module has to be loaded first |
| <a id="modprobe-option"></a>**modprobe option** | A setting for a kernel module, written as `options <module> <name>=<value>` in a file under `/etc/modprobe.d/`. `install` writes a few of these. See [Modprobe files](installation.md#modprobe-files) |
| <a id="display-manager"></a>**Display manager** | The service that starts the graphical login screen, such as `gdm`, `sddm` or `lightdm`. `activate` stops it only when you pass `--stop-display-manager` |
| <a id="vgpuconfig-xml"></a>**`vgpuConfig.xml`** | NVIDIA's list of the professional cards and vGPU types the vGPU software knows. GeForce cards are not in it, which is why the identity hook is needed |
| <a id="totalvfs"></a>**TotalVFs** | The number of VFs a card says it can have. geforce-sriov presents up to this many, 4 by default. Most Ada cards report 1, which geforce-sriov treats as 4. See [Capability positions per generation](devices.md#capability-positions-per-generation) |
| <a id="runtime-power-management"></a>**Runtime power management** | NVIDIA's driver powering an idle GPU down on its own, set by `NVreg_DynamicPowerManagement`. On a laptop it must be off, because a GPU that powers off loses its SR-IOV setup. See [D3cold](laptops.md#d3cold) |
| <a id="host-driver"></a>**Host driver, guest driver** | NVIDIA's vGPU software has two halves. The host driver package for Linux KVM, `NVIDIA-Linux-x86_64-<version>-vgpu-kvm.run`, is installed on the host. A guest driver is installed in each VM. See [Supported software stack](installation.md#supported-software-stack) |
| <a id="stock"></a>**Stock** | NVIDIA's own, unchanged file. The stock module is NVIDIA's `nvidia.ko` and the stock plugin is NVIDIA's `libnvidia-vgpu.so.<version>` |
| <a id="nvidia-vgpud"></a>**`nvidia-vgpud`** | NVIDIA's daemon that registers the vGPU types of each GPU when it starts, then exits. The identity hook is loaded into it |
| <a id="nvidia-vgpu-mgr"></a>**`nvidia-vgpu-mgr`** | NVIDIA's daemon that runs the vGPUs and loads the vGPU plugin. Restarting it ends the vGPU of every running VM, so restart it only through `activate` |
| <a id="sriov-manage"></a>**`sriov-manage`** | NVIDIA's script that enables or disables the VFs of a card. `activate` runs it for a selected card that has no VFs. The `sriov_manage` key in the config names its path |
| <a id="nouveau"></a>**`nouveau`** | The open-source NVIDIA driver that Linux loads by default. It must not be loaded. `install` refuses while it is |
| <a id="generation"></a>**Generation** (Ampere, Ada) | The chip family of a card, Ampere or Ada. For example, the GeForce RTX 30 series is Ampere and the RTX 40 series is Ada. The generation decides the professional counterpart and the default vGPU type |
| <a id="die"></a>**Die** | The chip on the card, for example GA102 or AD104. `geforce-sriov devices` prints it for every listed card |
| <a id="device-table"></a>**Device table** | The list of PCI device IDs geforce-sriov acts on, in `include/gs_devices.h`. `geforce-sriov devices` prints it. See [Supported cards](devices.md) |
| <a id="professional-counterpart"></a>**Professional counterpart** (vGPU target) | The professional card under whose device ID a selected card is presented to NVIDIA's vGPU software. It is the RTX A6000 (`10de:2230`) for Ampere and the RTX 6000 Ada (`10de:26b1`) for Ada |
| <a id="selection"></a>**Selection** | The cards you chose, listed as `bdfs` in the config. The kernel module, the identity hook and `activate` act only on them |
| <a id="confirmed-version"></a>**Confirmed version, confirmed inputs** | Host driver 580.159.01. Its files, and every file `install` produces from them, match SHA-256 digests recorded in geforce-sriov. The build record then says `confirmation=confirmed-inputs`. See [Supported inputs](driver-patch.md#supported-inputs) |
| <a id="best-effort"></a>**Best effort (unconfirmed build)** | A build from NVIDIA files with other digests, made when each byte sequence to change is found exactly once. It is recorded as `confirmation=unconfirmed` and is not guaranteed to work |
| <a id="host-object"></a>**Host object** (`nv-kernel.o_binary`) | The precompiled part of NVIDIA's kernel module, in NVIDIA's kernel source tree. `install` changes a copy of it and builds `nvidia.ko` from that copy |
| <a id="revision"></a>**Revision** | One byte change that `install` makes in a copy of an NVIDIA file. The host object gets the scheduler, probe gate and VF count revisions, plus Ada placement when an Ada card is selected. The vGPU plugin gets two changes. See [Revisions](driver-patch.md#revisions) |
| <a id="code-window"></a>**Code window** | The bytes around a change. On a file of another version the patch tool finds the place by this sequence, which must occur exactly once |
| <a id="driver-step"></a>**Driver step** | The part of `install` and `rebuild` that patches copies of NVIDIA's files, rebuilds `nvidia.ko` for one kernel and installs it. The script `geforce-sriov-driver` does it. An `install` run writes its output to `/var/lib/geforce-sriov/driver-step.log` |
| <a id="build-record"></a>**Build record** | The file `/var/lib/geforce-sriov/driver-build`. It names a kernel and the SHA-256 and build-id of the `nvidia.ko` that the driver step built for it. The record of each other kernel is kept in `/var/lib/geforce-sriov/driver-builds/<kernel>`. `rebuild --kernel RELEASE` makes the one for that kernel. `activate` refuses when the installed module is not the one recorded for the running kernel |
| <a id="display-build"></a>**Display build** | A build of NVIDIA's kernel module that includes the display modules `nvidia-modeset` and `nvidia-drm`. It is in effect when a selected GPU is the boot display and `display` is not `off` |
| <a id="host-cuda"></a>**Host CUDA** | The optional feature `host_cuda=on`. It builds `nvidia-uvm` and installs NVIDIA's CUDA library, so that CUDA programs can run on the host. See [Host CUDA](installation.md#host-cuda) |
| <a id="host-desktop"></a>**Host desktop** | The optional feature `host_desktop`. It installs NVIDIA's graphics libraries, so that the boot display GPU draws the X11 desktop of the host. See [Host desktop](installation.md#host-desktop) |
| <a id="kernel-hook"></a>**Kernel hook** | The script `install` places where the package manager runs it after a kernel or its headers are installed. It runs `geforce-sriov rebuild --kernel RELEASE` for the new kernel. See [After a kernel update](installation.md#after-a-kernel-update) |
| <a id="drop-in"></a>**Drop-in** | A small systemd file that adds settings to an existing service. `install` writes one for `nvidia-vgpud` and one for VM autostart. See [Systemd units](configuration.md#systemd-units) |
| <a id="source-folder"></a>**Source folder, installed copy** | The source folder is the extracted release in which you ran `make`. Commands there start with `./geforce-sriov`. The installed copy is the program that `install` put in `/usr/local/bin`, the default prefix |
| <a id="staged-install"></a>**Staged install** | An `install --destdir PATH` run, which only copies files below `PATH` and changes nothing on the running host |
| <a id="manual-path"></a>**Manual path** | Installing with `--driver=skip` and making the changes to NVIDIA's files yourself. See [The manual path](driver-patch.md#the-manual-path) |
| <a id="preflight"></a>**Preflight** | The read-only checks `activate` makes before it changes anything. A refusal here changes nothing, and `activate --dry-run` stops after them |
| <a id="re-probe"></a>**Re-probe** | Unbinding a card from NVIDIA's driver and binding it again. The card stays on the PCI bus |
| <a id="remove-and-rescan"></a>**Remove and rescan** | Taking a card off the PCI bus and letting the kernel find it again, so that the kernel reads the revealed capabilities. `activate` does it once for a card that does not show SR-IOV yet |
| <a id="vf-power-gate"></a>**VF power gate** | The requirement that every VF has `power/control=on` and `runtime_status=active` before a VM starts. `activate` sets both and `check` verifies them |
| <a id="vm-video-memory-change"></a>**VM video memory change** (Ada placement change) | The change `install` builds into `nvidia.ko` when an Ada card is selected. An Ada VM takes one free piece of video memory when it starts, and no VF has a fixed range. See [VM video memory](ada.md#vm-video-memory) |
| <a id="fixed-slot"></a>**Fixed slot**, `placement_id` | On an Ada card whose loaded module lacks the VM video memory change, each VF has a fixed range of the card's video memory. This range is called a slot. `nvidia/placement_id` of the VF shows it, or `Not Applicable` when there is none |
| <a id="d3cold-consent"></a>**D3cold consent** | The config line `d3cold=off`. It means you agree that `activate` keeps a laptop GPU powered. Without it `activate` refuses a selection that holds a laptop GPU. See [Consent](laptops.md#consent) |
| <a id="rm"></a>**RM** (Resource Manager) | The core of NVIDIA's driver. With GSP off it runs on the host CPU, which NVIDIA calls CPU-RM. The identity hook changes two of its answers |
| <a id="rmsetvgpugsppluginoffloadmode"></a>**`RMSetVgpuGspPluginOffloadMode`** | A setting of NVIDIA's guest driver that every guest needs at `0`. It is a modprobe option in a Linux guest and a registry value in a Windows guest. See [Guests](installation.md#guests) |
| <a id="above-4g-decoding"></a>**Above 4G decoding** | A firmware setting that lets PCI devices use memory addresses above 4 GB. It gives the bridges above the card room for the BARs of the VFs |
| <a id="bridge"></a>**Bridge** (root port) | The PCI device directly above the card. `activate` rescans the bus below it, and its memory window must hold the BARs of the card and of the VFs |
| <a id="run-lock"></a>**Run lock** | The file `/run/geforce-sriov/lock`, which keeps two geforce-sriov commands from changing the host at the same time. It is not the activation lock |
